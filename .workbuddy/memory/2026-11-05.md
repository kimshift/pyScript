## 【磁盘治理·续】重启后环境变量仍未继承 → 改用目录联接兜底

现象：用户重启 WorkBuddy 后，进程仍**没有** MISE_DATA_DIR / UV_CACHE_DIR / PIP_CACHE_DIR（注册表 HKCU\Environment 里确实存在，但进程树由旧环境派生，拿不到）。后果：`mise ls` 报 python/uv "missing"，`mise exec -- python` 触发自动安装，**又往 C 盘装了 93MB**（%LOCALAPPDATA%\mise）。

修复（不依赖环境变量）：
- 删除 C 盘重复目录，建立三个 **junction**：
  `%LOCALAPPDATA%\mise` → `D:/Program/mise`
  `%LOCALAPPDATA%\uv`   → `D:/Program/mise/cache/uv`
  `%LOCALAPPDATA%\pip`  → `D:/Program/mise/cache/pip`
- 缓存层级归一：把 `cache\uv\*`、`cache\pip\*` 各下沉到 `cache\uv\cache\`、`cache\pip\cache\`，并把用户变量改为
  `UV_CACHE_DIR=D:/Program/mise/cache/uv/cache`、`PIP_CACHE_DIR=D:/Program/mise/cache/pip/cache`
  这样「有变量的进程」和「没变量走 junction 的进程」实际用的是同一个物理目录，不会重复下载。

验证（无环境变量下）：`mise ls` 正常识别工具；`sys.executable` 显示 C 路径但 `os.path.realpath()` = `D:/Program/mise/installs/python/3.13.18/python.exe`；两条缓存路径 realpath 一致；`.venv` 的 base 与 site-packages 均在 D；`mise run ld:check` 正常。

C 盘余量 38.73 GB；C 盘已无实体 Python 落点（仅 WindowsApps 存根、`.venv-html-to-docx` 属其它工具、用户 11-4 自建的 `Temp\misetest_venv`，基座在 D）。
结论：**以后遇到「mise/uv 又往 C 盘装」的报障，先查 junction 是否被破坏，而不是查环境变量。**

## 【依赖·结论修正】opencv-python-headless 在 Windows 上并不省空间

- 我原先判断「换 headless 可省约 70MB」——**实测错误**。
- 实测 headless 4.14.0.94 安装后 `cv2` 目录 **110.4MB**，与 full 版几乎相同。构成：`cv2.pyd` 71.3MB + `opencv_videoio_ffmpeg4140_64.dll` 29.1MB，GUI 部分可忽略不计；Windows 下 full 版的 GUI 后端是内建 `WIN32UI`（`cv2.getBuildInformation()` 可见），没有独立 Qt 目录。
- 已改回 `opencv-python==4.14.0.94`（保留 `cv2.imshow` 调试能力），`uv lock --check` 通过，venv 167MB。
- **坑**：`opencv-python` 与 `opencv-python-headless` 共用 `cv2/` 命名空间，`uv sync` 切换时只按 RECORD 删文件，会残留旧文件（表现为切到 headless 后 `cv2` 仍 111MB、imshow 仍在）。正确做法：先删 `.venv/Lib/site-packages/cv2`，再 `uv sync --reinstall-package <包名>`。
