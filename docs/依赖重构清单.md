## 0. 一句话结论

**"不兼容"目前还不是事实，"没人维护"才是事实。**

8 个依赖里 5 个仍在活跃维护，**2 个已停止维护**（`PyAutoGUI` 2023-05 后无发布；`keyboard` 仓库已归档），1 个落后一个 minor（`APScheduler`）。在 Python 3.13 上实测：截图、模板匹配、热键监听、进程管理**全部可正常工作**，项目不会因为换 3.13 而跑不起来。

真正的风险结构是：
- **单点风险**：`PyAutoGUI` 承担 22 处调用（点击/输入/截图/弹窗），一旦它随 Pillow 或 Python 演进失效，项目直接瘫痪。
- **性能瓶颈**：每次 `location()` = 全屏截图(62ms) + 全屏灰度匹配(173ms) ≈ **0.24s**，而 `wait_click` 是循环调用。
- **可复现性缺口**：`mise.toml` 只锁了 Python 版本，依赖版本仍靠 `requirements.txt` 手写 pin，无 lock、无 venv。

推荐走 **方案 B（替换停更点，保留成熟点）**，分 4 期落地，见第 5 节。

## 3. 风险清单（按影响面排序）

### R1 🔴 PyAutoGUI 已停更，且是最大调用面

- **现象**：0.9.54 是 2023-05 的版本，也是 PyPI 上唯一稳定版；仓库无人工提交、issue/PR 无人处理，健康分被评到 "At Risk"。
- **影响**：22 处调用（鼠标、键盘、截图、弹窗）全压在它上面，底层依赖链是 `pyautogui → pyscreeze / pymsgbox / pytweening / mouseinfo → Pillow`。**Pillow 每次大版本变动都可能把它弄坏**——历史上 pyscreeze 移除 `grab` 函数就导致过 `locateOnScreen` 全线报错（社区有记录）。
- **触发条件**：Pillow / Python 再升一代；或需要多显示器、HiDPI 场景。
- **已确认的能力边界**：只支持**主显示器**，不支持多屏坐标；不处理 DPI 缩放（进程非 DPI-aware 时，`size()` 与物理分辨率不一致，点击坐标会整体偏移）。
- **建议**：不要指望它修，按第 4 节方案 B 把它降级为"可替换的一层壳"。

### R2 🔴 keyboard 已归档，却承担急停职责

- **现象**：最后版本 0.13.5（2020 年），仓库已归档。
- **影响**：`common.py` L190 / L370 的 `keyboard.is_pressed('f8')` 是**唯一的运行时急停手段**（配合 `pyautogui.FAILSAFE`）。它一旦在低层钩子上失效，脚本只能靠 `Ctrl+C` 或杀进程来停——而脚本正在抢占鼠标键盘，用户很难操作。
- **触发条件**：Windows 安全软件拦截全局钩子、非管理员权限运行、未来 Python 版本变更。
- **建议**：换 `pynput`（活跃维护，纯 Python，`keyboard.Listener` 同一套底层钩子），并用"监听回调写状态位"替代"循环里轮询"。

### R3 🟠 全屏模板匹配是性能与稳定性的共同瓶颈

- **现象**：`location()` 每次全屏匹配 ≈0.24s（实测），`wait_click` 与 `Buttons.find` 都是循环调用。
- **影响**：① 单步操作慢，批量 25 个模拟器时累计分钟级；② 全屏匹配 0.8 阈值在复杂界面易误命中（本例单模板极限相关度只有 0.38，说明该图当前根本不在屏幕上，阈值语义必须靠"仅在目标窗口区域内搜索"来兜）。
- **建议**：限定 ROI（只在雷电多开器窗口矩形内匹配）、模板灰度预转换缓存、一次截图供多次匹配复用。

### R4 🟠 opencv 5.0 是破坏性大版本，别跟风升

- **现象**：`opencv-python` 已发 5.0.0.93（2026-07），4.x 线最新 4.14.0.94。
- **影响**：5.0 有 API 移除/重排，`matchTemplate` 虽然稳，但周边（`imread` 参数、常量命名、DNN 模块）会有坑。
- **建议**：**停在 4.x 线**，升到 4.14 即可；5.0 等生态明确后再单独评估。

### R5 🟡 APScheduler 落后一个小版本；4.0 不能碰

- **现象**：3.10.4 → 3.11.3（2026-06-28），3.11 修了 ZoneInfo 下的 DST 停滞、`six` 依赖移除。4.0 仅到 `4.0.0a6`（2025-04），官方 README 原话是"可能不兼容变更且无迁移路径，**不要**用于生产"。
- **影响**：`scheduler.py` 用 `timezone='Asia/Shanghai'` + cron，3.11 的 DST 修复对它有益。
- **建议**：升 3.11.3，**锁死在 3.x**，并在 requirements 里注释"勿升 4.x"。

### R6 🟡 中文路径 + `cv2.imread` 会静默失败

- **现象**：`config.json` 里 `emulator_install_path` 已是 `D:\records\仓库\安装包\雷电安装包` 这种中文路径；`common.py` L75 用 `cv2.imread(img_path)` 读模板，而 Windows 下 `cv2.imread` 对非 ASCII 路径**返回 None 而不抛异常**。
- **影响**：一旦把 `public/image` 或整个项目挪到中文路径，`template.shape` 处抛 `AttributeError: 'NoneType'`，被 L95 的 `except Exception` 吞掉，表现为"永远找不到按钮"，极难排查。
- **建议**：统一用 `np.fromfile(path, dtype=np.uint8)` + `cv2.imdecode` 读图；或启动时断言图片目录可读。

### R7 🟡 依赖不可复现

- **现象**：`mise.toml` 只锁 Python 版本；依赖版本靠 `requirements.txt` 手写 `==`，没有 hash lock，也没有 venv，直接装进 mise 的全局 site-packages。
- **影响**：换机器/重装后无法保证装出同一组二进制；全局安装还容易与其它项目互相污染。
- **建议**：短期用 `.venv` + `pip freeze` 出 `requirements.lock.txt`；中期换 `uv`（`uv pip compile` / `uv sync`，自带 lock 且比 pip 快一个量级）。

## 4. 可选方案对比

| 方案 | 核心动作 | 改动面 | 工期 | 收益 | 风险 | 适合什么时候选 |
|---|---|---|---|---|---|---|
| **A 保守升级** | 只升仍在维护的库（opencv 4.14 / numpy 2.5 / Pillow 13 / psutil 7.2 / pyperclip 1.11 / APScheduler 3.11.3），`pyautogui`、`keyboard` 原样锁死 | 仅 `requirements.txt` | 0.5 天 | 修掉 DST bug、拿到安全补丁，风险≈0 | 停更风险仍在，天花板低 | 只想"别出事"，近期没有新功能 |
| **B 替换停更点** ⭐ | A + `keyboard → pynput`、`pyautogui.screenshot → mss`、弹窗换 `tkinter.messagebox`、新增 `adapters` 适配层，`pyautogui` 只保留点击/输入 | `common.py` 拆新模块 + 4-5 个调用点改写 | **1.5–2 天** | 铲掉两个停更依赖、截图提速、急停更可靠、为后续替换留接口 | 中等：输入行为差异需回归 | **推荐**，投入产出比最高 |
| **C 架构重构** | B + 分层（截图/输入/图像/配置/日志）+ 明确状态机 + 失败重试与截图留证 | 全量重构 `common.py`/`emulator.py`，新增 6-8 个模块 | 1–2 周 | 可测试、可观测、可扩展，新增动作不必再改底层 | 高：改动面大，GUI 行为回归成本高 | 打算长期维护、或要加"失败自愈"能力 |
| **D 不动**（对照项） | 保持现状 | 0 | 0 | 零成本 | Python/Pillow 下一次升级就可能全线崩，且无退路 | ❌ 不建议，仅作基准对照 |

### 方案 B 的逐项替换对照

| 能力 | 现在用的 | 替换为 | 迁移成本 | 注意点 |
|---|---|---|---|---|
| 鼠标点击/移动/拖拽 | `pyautogui.click/moveTo/mouseDown` | 短期**保留** `pyautogui`；若要更"像真人"，换 `pydirectinput`（扫脚本，对模拟器更友好） | 低（封装即可） | `pydirectinput` 同样只支持主屏、不处理 DPI |

## 7. 回归验证方法

### 7.1 冒烟脚本（不产生鼠标动作）

```python
# scripts/smoke.py —— 只验证"库能不能用"，不点任何东西
import json, os, sys
import cv2, numpy as np, psutil, pyperclip
import pyautogui

root = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
shot = pyautogui.screenshot()
arr = cv2.cvtColor(np.array(shot), cv2.COLOR_RGB2GRAY)

results = {"cv2": cv2.__version__, "numpy": np.__version__,
           "screen": list(pyautogui.size()), "templates": {}}
for dirpath, _, files in os.walk(os.path.join(root, "public", "image")):
    for fn in files:
        if not fn.endswith(".png"):
            continue
        tpl = cv2.imread(os.path.join(dirpath, fn), cv2.IMREAD_GRAYSCALE)
        if tpl is None:                      # 中文路径会静默返回 None
            results["templates"][fn] = "READ_FAILED"
            continue
        res = cv2.matchTemplate(arr, tpl, cv2.TM_CCOEFF_NORMED)
        results["templates"][fn] = round(float(cv2.minMaxLoc(res)[1]), 4)

print(json.dumps(results, ensure_ascii=False, indent=2))
```

### 7.2 匹配基线对比

改造前后各跑一次，**同名模板的 max_val 偏差应 < 0.02**；偏差超出的，基本都是截图通道（pyautogui → mss）颜色空间搞错了（RGB vs BGR vs BGRA）。

### 7.3 行为回归（必须人工看）

`create` / `create_con` 是长链路（创建→设置→启动→装包→同步→权限），建议：
1. 先跑 `create_con` 的**只读段**（`sort_win` → 定位按钮 → 打印坐标，不点击）；
2. 全程录屏，改造前后各一遍，对比每个按钮的落点；
3. 用 `config.json` 里 `batch_start_num` 调成 1，缩短单次回归时间。

## 9. 决策建议（给决策者的三行）

1. **现在不要大动**：3.13 上实测能跑，先按 Phase 0 + Phase 1（1 天工作量）把基线和不冒烟的升级做掉。
2. **优先掏掉 `keyboard`**：它已归档却握着"急停"这条命脉，替换成本最低（半天），收益最直接。
3. **`pyautogui` 不必立刻换**：它虽停更但 API 极稳定，正确做法是**先加适配层把它隔离**，等真坏了再换实现——而不是现在就全量重写。
