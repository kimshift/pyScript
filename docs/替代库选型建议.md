# 替代库选型建议 —— 从"换更好的库"到"换更合适的控制途径"

> 编写日期：2026-11-05  
> 项目：pyScript（雷电模拟器批量自动化）  
> 前置文档：[`依赖重构清单.md`](./依赖重构清单.md)（兼容性与风险清单）、[`./项目代码审查报告.md`](./项目代码审查报告.md)（逻辑缺陷）  
> 本文回答一个问题：**如果目标是"更好、更适配、更优秀"，到底该换什么？**
> ⚠️ **路径说明**：文中 `src/emulator.py`、`public/image/` 指的是重构前的位置，现为 `tools/ld_emulator/`，对照见 [`项目结构规范.md`](./项目结构规范.md)。

> ✅ **落地进度（2026-11-05）**
> - **R1 CLI 接管：已完成**。新增 `tools/ld_emulator/backends/ldconsole.py`，接管 create/start/install/backup/restore/sortWnd/quit/list2；`config.json` 的 `backend` 可在 `cli`/`gui` 间切换回滚。
> - **R2 换停更库：已完成**。截图 → `mss`（灰度逐像素对比与原方案差异 0/255）、热键 → `pynput`（事件回调）、弹窗 → `tkinter`、`keyboard` 与 `APScheduler` 依赖已移除。
> - **R3 收窄 GUI：已完成**。同步器与应用内权限集中在 `open_async`/`close_async`/`app_setting`，其余动作不再依赖图像匹配。
> - **R4（OCR / ADB 接管 App 内操作）：未做**，按原计划推迟。

## 0. 结论先说

**这个项目最该换的不是库，而是"用鼠标点界面"这件事本身。**

本机实测确认：雷电自带 `ldconsole.exe`（v9.1.68.0），`help` 里列出的 `add / copy / modify / launch / quit / installapp / backup / restore / sortWnd / adb` 等命令，**直接对应你现在用图像匹配+点击实现的 9 个业务动作中的 10 个**。用它的收益是量级差别：

| 维度          | 现在（GUI 点击）           | 换成 ldconsole       |
| ----------- | -------------------- | ------------------ |
| 单次操作耗时      | 0.24s 起（截图+匹配）+ 点击延时 | 进程调用 ~50-150ms，无匹配 |
| 分辨率/DPI 变化  | 全流程失效                | 完全无关               |
| 窗口被遮挡/最小化   | 找不到按钮                | 不受影响               |
| 25 个模拟器批量操作 | 十几分钟，全程不能动鼠标         | 秒级，可后台跑            |
| 界面改版/换皮肤    | 48 张模板图全废            | 无关                 |

所以真正的方案是 **三层降维**：

1. **控制层**（新增）：`ldconsole.exe` + `adb` —— 接管能接管的一切；
2. **兜底层**（缩小）：`mss` 截图 + `pyautogui` 点击 —— 只留给 `ldconsole` 做不到的操作（主要是**同步器**）；
3. **基础库**（精简）：`keyboard → pynput`、删 `APScheduler`、弹窗换标准库 —— 从 8 个依赖降到 7 个，且全是活跃维护的。

## 2. 业务动作映射表：GUI 点击 → 官方命令

| #  | 业务动作          | 现有实现（`src/emulator.py`）                   | 建议实现                                                                                                             | 收益              |
| -- | ------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------- |
| 1  | 批量创建 N 个模拟器   | `buttons.click("批量新增")`（L196-197）         | `ldconsole add --name 雷电{id}` × N，或 `copy --from 雷电0 --name 雷电{id}`                                              | 免点击，可精确命名       |
| 2  | 设置分辨率/内存/设备参数 | `batch_setting()` 连点 9 步（L65-83）          | `ldconsole modify --index {i} --resolution 1080,1920,480 --memory 4096 --cpu 4`                                  | **9 步 → 1 条命令** |
| 3  | 批量启动          | `search(id)` + `click('启动')`（L48-62）      | `ldconsole launch --index {i}`                                                                                   | 去掉搜索框依赖         |
| 4  | 批量安装 APK      | APK选项→路径搜索→粘贴→文件打开（L106-123）              | `ldconsole installapp --index {i} --filename "D:\...\x.apk"`                                                     | 无文件对话框、无中文路径风险  |
| 5  | 应用权限设置        | 拖拽 + 逐项点击坐标（L150-181）                     | `ldconsole adb --index {i} --command "shell pm grant {pkg} android.permission.READ_PHONE_STATE"`（或 `appops set`） | 权限可枚举、可断言       |
| 6  | 备份模拟器         | 备份/还原→粘贴路径→文件保存（L235-258）                 | `ldconsole backup --index {i} --file "D:\backup\雷电-{i}.ldbk"`                                                    | 无对话框            |
| 7  | 还原模拟器         | 同上（L261-288）                              | `ldconsole restore --index {i} --file "..."`                                                                     | 同上              |
| 8  | 排列窗口          | `buttons.click("排列窗口")`（L39-45）           | `ldconsole sortWnd`                                                                                              | 一行              |
| 9  | 关闭模拟器         | `psutil` 模糊匹配进程名后 `kill()`                | `ldconsole quit --index {i}` / `quitall`                                                                         | 不会杀错进程          |
| 10 | 查询实例/状态       | 无（靠人眼看）                                   | `ldconsole list2` / `runninglist` / `isrunning --index {i}`                                                      | 可编程、可断言         |
| 11 | **开启/关闭同步器**  | `open_async()` / `close_async()`（L86-103） | ⚠️ **无 CLI 命令，必须保留 GUI**                                                                                         | 唯一无法迁移的动作       |

**结论：11 个动作里 10 个可以脱离 GUI。** 这就是"更适配"的实质。

## 3. 必须保留 GUI 的部分（诚实清单）

| 场景                         | 为什么 CLI 做不到                      | 保留方式                                      |
| -------------------------- | -------------------------------- | ----------------------------------------- |
| 开启/关闭**同步器**               | `ldconsole` 没有同步命令；同步是"多开器"的聚合操作 | `mss` 截图 + `pyautogui` 点击（原有图像匹配逻辑几乎原样保留） |
| 弹窗确认（"不在提示"、"不谢谢"）         | 属于多开器自绘弹窗，无对外接口                  | 同上（或用 `pygetwindow` 找窗口 + 固定坐标点击）         |
| 模拟器**内部**的 App 操作（如支付宝授权页） | 需要 App 内坐标，图像匹配仍是最直接办法           | ADB `input tap` 或保留图像匹配                   |

因此架构不是"删掉 GUI 层"，而是把它从**主线**降为**支线**——影响面从"整个流程"缩到"一步"。这也意味着：**分辨率变化时，只有同步器那一步会坏，其它 10 个动作照常工作。**

## 4. 库层替换清单（逐项）

| 现依赖                                         | 建议                     | 目标版本          | 为什么换                                                                | 迁移成本              |
| ------------------------------------------- | ---------------------- | ------------- | ------------------------------------------------------------------- | ----------------- |

## 5. 建议的分层架构

```text
┌─────────────────────────────────────────────────────────┐
│ 业务层  emulator.py：create / start / backup / restore   │
│         （不再直接调用 pyautogui / cv2）                  │
└───────────────┬─────────────────────────┬───────────────┘
                │ 90% 动作                 │ 10% 动作
┌───────────────▼──────────────┐  ┌───────▼───────────────┐
│ L1 控制层（新增，首选）        │  │ L2 兜底层（收窄）      │
│  backends/ldconsole.py       │  │  adapters/screen.py   │
│  · add/copy/modify/launch    │  │    mss 截图 + ROI     │
│  · installapp/backup/restore │  │  adapters/click.py    │
│  · adb --command             │  │    pyautogui 点击      │
│  纯 subprocess，无 UI 依赖    │  │  仅同步器/弹窗/App 内  │
└───────────────┬──────────────┘  └───────┬───────────────┘
                │                         │
┌───────────────▼─────────────────────────▼───────────────┐
│ 基础层  opencv(模板匹配) · numpy · Pillow                 │
│ 工具层  pynput(急停) · psutil(进程) · pyperclip(中文)     │
│         tkinter(对话框) · logging(替代 print)            │
└─────────────────────────────────────────────────────────┘
```

好处很具体：

- 新增一个业务动作时，**先问"有没有 ldconsole 命令"**，有就 3 行代码搞定；
- 只有"同步器"这类没有接口的动作，才走图像匹配，且分辨率变化只影响这一处；
- 想彻底摆脱 GUI 时，只需删 L2，不影响 L1。

## 6. 为什么不选那些"看起来更专业"的方案

| 候选                           | 定位                      | 对本项目的适用性                                                | 结论                |
| ---------------------------- | ----------------------- | ------------------------------------------------------- | ----------------- |
| **pywinauto / uiautomation** | Windows 控件树自动化          | 雷电多开器是 Qt 自绘界面，UI Automation 树里拿不到按钮（可用 Inspect.exe 验证） | ❌ 不适用             |
| **Airtest（网易）**              | 游戏自动化（图像识别 + Poco + 报告） | 看似最"适配"，但底层仍是 adb + 图像匹配，依赖重（含自己的私有格式与 IDE），迁移成本高于收益    | 🟡 备选，不建议现在引入     |
| **Appium**                   | 移动 App 端到端测试            | 面向真实设备/App 内部，绕不开 LDPlayer 的多开管理；太重太慢                   | ❌ 不适用             |
| **scrcpy + adb input tap**   | 设备镜像 + 坐标注入             | 能做，但每条命令 100–300ms，25 实例批量明显慢于 `ldconsole`              | 🟡 可作为 App 内操作的补充 |
| **Poco / uiautomator2**      | Android 控件树             | 模拟器内 App 若为原生控件可用，但当前场景（支付宝授权、桌面）多为自绘                   | 🟡 视具体 App 再评估    |
| **pydirectinput**            | 更"真实"的键鼠注入              | 只在"必须点击"时才需要，属可选优化                                      | 🟢 可选             |

**判断原则**：能用官方 CLI 就不用图像识别；能用图像识别就不用通用 GUI 框架；专用测试框架（Airtest/Appium）只在"要测 App 内部"时才值得引入。

## 8. 风险与注意事项

| 风险                     | 说明                      | 应对                                                           |
| ---------------------- | ----------------------- | ------------------------------------------------------------ |
| `ldconsole` **无退出码语义** | 命令返回 0 不代表操作成功          | 每次动作后用 `list2`/`runninglist`/`isrunning` 复核状态                |
| 输出格式是逗号分隔、无 header     | `list2` 的字段顺序靠约定        | 写一层解析并加单元测试；字段数变化时报错而非静默                                     |
| 命令随雷电版本变化              | 当前 9.1.68.0，升级后参数可能变    | 启动时校验 `ldconsole help` 是否含所需关键字，不匹配则告警                       |
| 同步器仍依赖 GUI             | 分辨率/DPI 变化仍会影响这一步       | R3 把它隔离成独立模块，坏掉时其它功能不受影响                                     |
| CLI 与 GUI 混用           | CLI 启动的实例窗口句柄需重新获取      | 统一从 `list2` 的窗口句柄字段取值，别硬编码坐标                                 |
| 中文路径                   | `subprocess` 传中文路径需正确编码 | 用 `subprocess.run(..., encoding='gbk')` 或全程 `pathlib` + 列表参数 |

## 9. 一页总结（给决策者）

1. **别只盯着换库**：`pyautogui` 换 `pynput`/`mss` 只能解决"维护性"，解决不了"分辨率一变全崩"；`ldconsole` 能解决后者，而且是官方接口、零新依赖。
2. **先修一个真 bug**：`config.json` 的模拟器路径是错的，现在 `open_app()` 根本起不来。
3. **性价比最高的两天**：R1（CLI 接管 4 个动作）+ R2（换掉两个停更库），之后项目处于"依赖全活跃、核心流程不依赖像素"的状态。
4. **`pyautogui` 不必消失**：把它从 22 处调用压到 8 处以内、隔离在一个 adapter 里，就是最优解——**隔离比替换更划算**。
