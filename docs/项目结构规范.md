# 项目结构规范 —— 多脚本仓库

> 编写日期：2026-11-05
> 适用范围：本仓库内所有 Python 脚本（现在只有雷电模拟器，以后会持续增加）
> 背景：仓库定位从「一个雷电脚本项目」变成「个人 Python 脚本集合」，因此结构、依赖、入口都需要统一约定，否则脚本一多就会互相踩。

---

## 1. 四条硬规则

| # | 规则 | 违反后的典型后果 |
|---|---|---|
| 1 | **一个脚本一个目录**：`tools/<脚本名>/`，目录名 = 模块名 = 命令名 | 两个脚本抢同一个模块名（原 `common.py`/`data.py` 这种名字一旦有第二个脚本就会冲突） |
| 2 | **依赖只在根 `pyproject.toml` 声明**，脚本目录里不写 `requirements.txt` | 依赖散落各处，装环境时漏装/版本打架 |
| 3 | **公共能力进 `kit/`，业务逻辑不进** | `kit` 变成一个什么都往里丢的垃圾桶，改一处影响全部脚本 |
| 4 | **入口只有两种**：`mise run <task>` 或 `python -m tools.<脚本名>` | 出现 `python tools/x/main.py`、`sys.path.insert(...)`、双击 py 文件等无法复现的跑法 |

## 2. 目录契约

| 路径 | 放什么 | 不放什么 |
|---|---|---|
| `pyproject.toml` | 依赖分组、工具配置（ruff/pytest） | 业务代码 |
| `uv.lock` | 锁定文件，**必须提交** | — |
| `mise.toml` | 运行时版本、所有命令入口 | 长脚本逻辑（超过 3 行就写进代码里） |
| `kit/` | 路径、配置读写、日志等**与业务无关**的能力 | 任何跟雷电/模拟器相关的东西 |
| `tools/<名>/` | 该脚本的代码、配置、资源，**自包含** | 跨脚本共享的代码（应上提 kit） |
| `tools/<名>/config.json` | 该脚本自己的配置 | 别的脚本会读的公共配置 |
| `tools/<名>/assets/` | 图片、模板、数据文件 | 生成物（如 `cache.txt`，走 gitignore） |
| `scripts/` | 仓库级工具脚本（脚手架、发布） | 业务脚本 |
| `tests/legacy/` | 历史手工验证脚本，不纳入 pytest | 正式单元测试（放 `tests/` 根） |
| `docs/` | 方案、规范、审查报告 | 代码 |

> 「自包含」的含义：只把 `tools/<名>/` 整个目录拷走，配上 `pyproject.toml` 里对应依赖组，脚本就应该能跑（这是容错设计，不是必须做到）。

## 3. 依赖规范（共享环境 + 分组）

### 3.1 为什么共享一个环境

个人脚本集合的依赖重合度很高（都有 cv2 / psutil / requests 这类），共享一个 `.venv` 的好处是：
- 装一次全能用，磁盘只占一份；
- 脚本之间可以互相 `import`，公共代码复用零成本；
- `uv.lock` 只有一份，回滚/复现简单。

### 3.2 分组写法

```toml
[project]
dependencies = ["psutil==6.1.0", "pyperclip==1.9.0"]   # 基础：几乎每个脚本都用

[project.optional-dependencies]
ld  = ["pyautogui==0.9.54", "opencv-python==4.10.0.84", "numpy==2.1.3"]
dev = ["pytest>=8.0", "ruff>=0.6"]
```

- 基础依赖 → `dependencies`
- 只被某一类脚本用到的 → 一个 group 一个名字，按功能命名（`ld` / `ocr` / `net`），不要按脚本名堆（`mytool1`、`mytool2` 这种组名说明该合并）
- 开发工具 → `dev`

### 3.3 逃生舱：什么时候必须单独建环境

共享环境有一个硬限制：**同一库的两个大版本无法共存**。出现下面任一情况，就该给那个脚本单独的环境，而不是硬塞进共享锁：

| 情况 | 例子 |
|---|---|
| 需要同一库的不同大版本 | A 脚本要 `opencv 4.x`，B 脚本要 `opencv 5.x` |
| 依赖体量巨大且互斥 | 一个要 `torch`（2GB+），另一个只要 `requests` |
| 依赖已停止维护、需要冻结 | 老脚本必须留在 `numpy 1.x` |

做法（不污染主环境）：

```sh
cd tools/<脚本名>
uv venv .venv                      # 该脚本自己的环境
uv pip install -r requirements.txt # 该脚本自己的依赖
uv run --python .venv python -m tools.<脚本名>
```

并在该脚本的 `README.md` 里写明「本脚本使用独立环境，原因：…」。

## 4. 代码规范

### 4.1 命名与入口

```
tools/<脚本名>/__main__.py     入口，只做参数解析 + 调用
tools/<脚本名>/__init__.py     写 ACTIONS 之类的清单或空文件
tools/<脚本名>/<业务模块>.py    业务实现
```

入口模板（保持统一，便于以后统一加日志/异常处理）：

```python
from kit.log import get_logger

log = get_logger(__name__)

def main(argv=None) -> int:
    return run(sys.argv[1:] if argv is None else list(argv))

if __name__ == "__main__":
    raise SystemExit(main())
```

### 4.2 路径：一律走 `kit.paths`

```python
from kit.paths import tool_dir   # ✅
ROOT = tool_dir("ld_emulator")

PROJECT_ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))   # ❌ 不要手算
```

原因是 `python -m` 运行的当前目录不固定，手算层级早晚算错（本次迁移就改了 3 处）。

### 4.3 日志与输出

- 新脚本用 `kit.log.get_logger()`，不要裸 `print` 打流程信息；
- 面向用户的最终结果可以 `print`（便于管道处理）；
- 退出码约定：`0` 成功、`1` 参数/配置错误、`2` 运行失败。**别用 `exit()` 直接抛**（原代码里有 `exit() if res else None` 这种写法）。

### 4.4 配置

- 每个脚本一份 `config.json`，放在自己目录下；
- 读写统一用 `kit.config.read_json/write_json`（UTF-8 + 中文不转义 + 末尾换行）；
- 配置里**不要放**跨脚本共享的路径（那种放环境变量或 `kit` 常量）。

## 5. 新增脚本 checklist

```sh
python scripts/new_tool.py my_tool
```

- [ ] `tools/my_tool/` 已生成（`__init__.py` / `__main__.py` / `README.md` / `assets/`）
- [ ] 依赖已加入 `pyproject.toml` 的某个 group（复用了已有组，或新建了功能命名的组）
- [ ] `mise.toml` 已加 task：`uv run --extra <组> python -m tools.my_tool`
- [ ] `mise run setup` 能装出环境
- [ ] `mise run <task>` 能跑通空实现
- [ ] 配置（如有）放 `tools/my_tool/config.json`
- [ ] 根 `README.md` 的「目录约定 / 命令」表格补了一行

## 7. 常见问题

**Q：能不能在任意目录下跑？**
不能直接 `python -m`。`python -m` 把**当前目录**加进 `sys.path`，所以要在仓库根执行。用 `mise run <task>` 则不必关心（mise 会在配置所在目录执行）。

**Q：VS Code 用哪个解释器？**
选 `.venv\Scripts\python.exe`（已在 `.vscode/settings.json` 设为默认）。不要选 mise 的全局 Python——那里面没装依赖。

**Q：想删掉一个脚本怎么办？**
删 `tools/<名>/` + 删 `mise.toml` 里对应 tasks + 从 `pyproject.toml` 移掉只有它在用的依赖 → `uv sync`。别留半截。

**Q：`kit/` 的代码要不要写测试？**
要。`kit` 被所有脚本依赖，坏了影响面最大；业务脚本反而可以先靠手工验证。
